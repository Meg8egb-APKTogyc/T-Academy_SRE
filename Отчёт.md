# Отчёт по домашнему заданию: клиент-серверное приложение «Трекер задач»

## Доменная область

Приложение — **трекер задач** (аналог простого issue tracker / todo-менеджера).
Пользователь ведёт список задач, группируя их по проектам. Для каждой задачи
отслеживаются статус выполнения, приоритет и срок.

## Стек реализации

| Компонент | Технология |
|---|---|
| Язык | Java 21 (LTS) |
| Бэкенд-фреймворк | Spring Boot 3.5 (Web, Data JPA, Validation, Actuator) |
| СУБД | PostgreSQL 16 |
| Миграции БД | Flyway |
| Сборка | Maven |
| Фронтенд | HTML + CSS + ванильный JavaScript (без сборки, раздаётся Spring Boot как статика) |
| Взаимодействие | HTTP/1.1, REST, JSON |
| Окружение | Docker, Docker Compose |

Стек выбран нересурсоёмким: один JVM-процесс со встроенным Tomcat, фронтенд без
node-этапа сборки.

## Основные сущности

**Project (проект)** — группа задач:

| Поле | Тип | Описание |
|---|---|---|
| id | bigint | PK, identity |
| name | varchar(200) | название, уникально, обязательно |
| description | varchar(2000) | описание |

**Task (задача)**:

| Поле | Тип | Описание |
|---|---|---|
| id | bigint | PK, identity |
| title | varchar(300) | заголовок, обязательно |
| description | varchar(5000) | описание |
| status | enum (NEW, IN_PROGRESS, DONE) | статус |
| priority | enum (LOW, MEDIUM, HIGH) | приоритет |
| due_date | date | срок выполнения |
| created_at | timestamptz | дата создания |
| project_id | bigint | FK → projects.id, при удалении проекта — SET NULL |

Связь: у проекта много задач, у задачи не более одного проекта.

## REST API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/tasks` | список задач (фильтры `?status=`, `?projectId=`) |
| GET | `/api/tasks/{id}` | задача по id |
| POST | `/api/tasks` | создать задачу |
| PUT | `/api/tasks/{id}` | обновить задачу |
| DELETE | `/api/tasks/{id}` | удалить задачу |
| GET/POST/PUT/DELETE | `/api/projects[/{id}]` | аналогичный CRUD для проектов |
| GET | `/api/info` | id экземпляра и hostname (пригодится для ДЗ по балансировке) |
| GET | `/actuator/health` | health-check |

Полный CRUD реализован для обеих сущностей и доступен как через API, так и через
веб-интерфейс (`http://localhost:8080/`).

## Соответствие методологии «12 факторов»

### I. Кодовая база (Codebase)
Единая кодовая база в одном git-репозитории. Из неё разворачивается любое число
окружений (локальная разработка, docker-compose, будущий прод) — различия только
в конфигурации через переменные окружения.

### II. Зависимости (Dependencies)
Все зависимости объявлены явно и с версиями в `pom.xml`; Spring Boot BOM фиксирует
совместимые версии. Приложение не полагается на системные пакеты: Docker-образ
собирается с нуля (`maven:3.9-eclipse-temurin-21` → `eclipse-temurin:21-jre`),
повторяемость сборки гарантирована.

### III. Конфигурация (Config)
Вся конфигурация, варьирующаяся между окружениями, вынесена в переменные
окружения: `SERVER_PORT`, `DB_URL`, `DB_USER`, `DB_PASSWORD`, `INSTANCE_ID`
(см. `application.yml` — там только чтение `${ENV:default}`, секретов в коде нет).
Шаблон — `.env.example`, реальный `.env` в `.gitignore`.

### IV. Сторонние службы (Backing services)
PostgreSQL — подключаемый ресурс, адрес которого берётся из `DB_URL`. Замена
локальной БД на managed-сервис (например, облачный PostgreSQL) требует только
смены переменной окружения, код не меняется.

### V. Сборка, релиз, запуск (Build, release, run)
Стадии строго разделены:
- **build**: `mvn package` (или стадия build в multi-stage Dockerfile) — компиляция и тесты, неизменяемый артефакт `task-tracker-1.0.0.jar`;
- **release**: Docker-образ = артефакт + конфигурация окружения;
- **run**: `java -jar` / `docker compose up`.
Каждый запуск использует готовый релиз, пересборки на старте нет.

### VI. Процессы (Processes)
Приложение stateless: сессий и in-memory состояния нет, всё состояние — в
PostgreSQL. Любой процесс можно убить и заменить, реплики взаимозаменяемы.

### VII. Привязка портов (Port binding)
Приложение self-contained: встроенный Tomcat слушает порт из `SERVER_PORT`
(по умолчанию 8080). Внешний веб-сервер не нужен — сервис сам экспортирует
HTTP через привязку к порту.

### VIII. Масштабируемость (Concurrency)
Масштабирование — горизонтальное, увеличением числа процессов-реплик за
балансировщиком: `docker compose up --scale app=3` (понадобится в ДЗ по
балансировке; эндпоинт `/api/info` показывает, какая реплика ответила).
Statelessness (фактор VI) это позволяет.

### IX. Утилизируемость (Disposability)
Быстрый старт (JAR стартует за несколько секунд) и корректное завершение:
включён graceful shutdown (`server.shutdown: graceful` — по SIGTERM сервер
перестаёт принимать новые запросы, дожидается завершения текущих и закрывает
пул соединений с БД). Проверено: при `kill <pid>` в логах `Graceful shutdown complete`.

### X. Паритет разработки и продакшена (Dev/prod parity)
Локально и в «проде» используются одни и те же backing services: PostgreSQL 16
поднимается через `docker-compose.yml` в обоих случаях, приложение запускается
из того же артефакта. Разрыв минимален: одинаковая СУБД, одинаковые миграции
Flyway, отличия только в значениях переменных окружения.

### XI. Логи (Logs)
Логи пишутся в stdout/stderr (стандартный Logback Spring Boot) как поток событий.
Приложение не управляет файлами логов — маршрутизация и хранение остаются на
окружении (docker logs, сборщик логов).

### XII. Административные процессы (Admin processes)
Задачи администрирования (миграции схемы БД) выполняются **той же кодовой базой
с той же конфигурацией**: Flyway-миграции (`src/main/resources/db/migration`)
применяются из того же артефакта при старте релиза либо как разовая команда
`mvn flyway:migrate` / `java -jar app.jar` с теми же переменными окружения.
Отдельной «админки» с собственной логикой доступа к БД нет.

## Запуск

Подробно — в `README.md`. Кратко:

```bash
# Только БД (для разработки из IDE):
docker compose up -d db
mvn spring-boot:run

# Или всё целиком в Docker:
docker compose up --build
```

Приложение: http://localhost:8080 , API: http://localhost:8080/api/tasks ,
health: http://localhost:8080/actuator/health .

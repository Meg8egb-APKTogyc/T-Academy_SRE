# Отчёт по ДЗ: Victoria Metrics + экспорт метрик приложения

## 1. Стек и развёртывание Victoria Metrics

- **Victoria Metrics (single-node)**: развёрнута в namespace `monitoring` через официальный Helm-чарт `victoria-metrics-single`.
- **vmagent**: развёрнут через Helm-чарт `victoria-metrics-agent`. Отвечает за сбор (scraping) метрик и отправку их в Victoria Metrics.
- **Spring Boot Actuator + Micrometer**: в приложение добавлена зависимость `micrometer-registry-prometheus`, открыт эндпоинт `/actuator/prometheus`.
- **PostgreSQL Exporter**: развёрнут как sidecar-контейнер (`prometheuscommunity/postgres-exporter`) в поде с базой данных, собирает метрики СУБД.

### Конфигурация чартов в репозитории

Параметры Helm-чартов зафиксированы в values-файлах в корне репозитория, чтобы не полагаться на дефолты чарта:

- `vm-single-values.yaml` — явно заданы: `replicaCount: 1`, `retentionPeriod: 14` (дней), `persistentVolume.enabled: true` с PVC размером `2Gi` (в дефолте чарта — 16Gi), ресурсы сервера (requests/limits).
- `vmagent-values.yaml` — scrape-конфигурация vmagent (см. раздел 4).

### Развёртывание одной командой

- `k8s/kustomization.yaml` — все манифесты проекта собраны в один kustomize-базис: `kubectl apply -k k8s/` разворачивает весь кластерный контур одной командой.
- `Makefile` — цель `make deploy` выполняет полный цикл:
  1. `helm repo add/update` с официальным репозиторием VictoriaMetrics;
  2. `helm upgrade --install vm-operator` — оператор VictoriaMetrics;
  3. `kubectl apply -k k8s/`
  4. `helm upgrade --install vm-single` (`-f vm-single-values.yaml`) и `helm upgrade --install vmagent` (`-f vmagent-values.yaml`).

## 2. Использованные экспортеры

1. **Рантайм и фреймворк (Pull)**: эндпоинт `/actuator/prometheus` на порту 8080. Отдаёт JVM-метрики (память, GC, потоки), метрики Tomcat и HikariCP.
2. **PostgreSQL (Pull)**: `postgres-exporter` на порту 9187. Отдаёт метрики базы данных (количество подключений, транзакции, `pg_up`).
3. **Бизнес-метрики (Pull)**: реализованы в приложении с помощью `MeterRegistry` (Micrometer) и отдаются через тот же эндпоинт Actuator.
4. **Blackbox-probe**: HTTP-пробы `/actuator/health` (backend) и `/` (frontend) через `VMProbe` (CRD от victoria-metrics-operator) + `blackbox-exporter` в namespace `monitoring`, каждые 15 секунд. Дублирующий статический `blackbox`-job в конфигурации vmagent убран, чтобы пробы не считались дважды.

## 3. Реализованные бизнес-метрики

В классе `BusinessMetrics.java` реализованы следующие метрики:

| Имя в коде (Micrometer)  | Имя в Prometheus                       | Тип     | Описание                                                 |
| ------------------------ | -------------------------------------- | ------- | -------------------------------------------------------- |
| `tasks_created_total`    | `tasks_total`                          | Counter | Общее количество созданных задач                         |
| `tasks_completed_total`  | `tasks_completed_total`                | Counter | Количество задач, переведённых в статус DONE             |
| `projects_created_total` | `projects_total`                       | Counter | Общее количество созданных проектов                      |
| `tasks_in_progress`      | `tasks_in_progress`                    | Gauge   | Текущее количество задач в статусе IN_PROGRESS           |
| `tasks_per_project`      | `tasks_per_project{project_id="..."}`  | Gauge   | Количество задач в каждом проекте (по тегу `project_id`) |
| `tasks_by_priority`      | `tasks_by_priority{priority="LOW"...}` | Gauge   | Распределение задач по приоритетам (LOW/MEDIUM/HIGH)     |
| `tasks_by_status`        | `tasks_by_status{status="NEW"...}`     | Gauge   | Распределение задач по статусам (NEW/IN_PROGRESS/DONE)   |

Три последних метрики — динамические gauge'и с тегами: значения пересчитываются group-by запросами из `TaskRepository` (`countTasksGroupByProject/Priority/Status`) после каждого изменения задач (создание/обновление/удаление), а также после удаления проекта. Для приоритетов и статусов значения проставляются для всех вариантов enum, даже если задач с таким значением нет (0). Пропавшие проекты обнуляются, чтобы series не «залипал» со старым значением.

Примеры запросов в vmui:

```promql
sum by (project_id) (tasks_per_project)
sum by (priority) (tasks_by_priority)
tasks_by_priority{priority="HIGH"} / sum(tasks_by_priority)
```

## 4. Сбор метрик (Service Discovery)

Для динамического обнаружения таргетов `vmagent` использует `kubernetes_sd_configs` (роль `pod`).
В манифесты деплойментов `backend` и `postgres` добавлены аннотации:

- `prometheus.io/scrape: "true"`
- `prometheus.io/port: "8080"` (для backend) / `"9187"` (для postgres)
- `prometheus.io/path: "/actuator/prometheus"` (для backend) / `"/metrics"` (для postgres)

Конфигурация `relabel_configs` в `vmagent-values.yaml` фильтрует поды по этим аннотациям и перенаправляет запросы на нужные порты и пути.

Лейблы пода не копируются в метрики напрямую: `labelmap` использует `replacement: pod_label_$1`, поэтому лейбл пода `app=postgres` попадает в метрику как `pod_label_app="postgres"`. Это исключает путаницу с лейблами, которые приложения и сервисы навешивают на собственные метрики. Лейблы `kubernetes_namespace` и `kubernetes_pod_name` добавляются явно.

## 5. Отдельный пользователь для PostgreSQL Exporter

Скрапер метрик PostgreSQL не использует приложение пользователя базы данных:

- Миграцией `V3__monitor_user.sql` создаётся роль `monitor` с `LOGIN` и выдаются `pg_monitor` (доступ к статистическим view СУБД), `CONNECT` на базу, `USAGE` на схему `public` и `SELECT` на таблицы схемы `public` (включая `ALTER DEFAULT PRIVILEGES` для будущих таблиц).
- Учётные данные exporter'а вынесены в отдельный Secret `postgres-exporter-secret` (`MONITOR_USER`/`MONITOR_PASSWORD`), не связанный с `db-secret` приложения.
- Sidecar `postgres-exporter` подключается через `DATA_SOURCE_URI` + `DATA_SOURCE_USER`/`DATA_SOURCE_PASS` из этого Secret — пароль приложения в манифесте не дублируется, а сам exporter зависит только от прав роль `monitor`.
